5. RAZORPAY SERVICE LOGIC  (RazorpayService.CreateOrderAsync)
────────────────────────────────────────────────────────────────────────────────

  Step 0  Idempotency check
            If IdempotencyKey already exists for this user, return existing
            Razorpay order details without creating a new internal order.

  Step 1  Load + validate cart
            GetBySessionKeyAsync → must exist and have items.

  Step 2  Verify address ownership
            GetByIdAndUserIdAsync → address must belong to the logged-in user.

  Step 3  Check delivery serviceability
            DeliveryService.CheckServiceabilityAsync(pincode).

  Step 4  Revalidate products + stock (server-side)
            For each cart item:
              - Product must be active
              - Inventory must be in stock
              - Quantity must be 1–20
              - AvailableQuantity >= requested Quantity
            Compute server-side line totals (OfferPrice ?? Price).
            *** Browser-submitted prices are never trusted. ***

  Step 5  Compute delivery fee
            Free delivery if subTotal >= FreeDeliveryAbove threshold.
            Check MinOrderValue constraint.

  Step 6  Create internal GOLIS Mart order
            OrderRepository.CreateOrderAsync — single transaction:
              INSERT Orders
              INSERT OrderItems
              UPDATE Inventory (deduct stock, optimistic concurrency)
              INSERT InventoryTransactions
              INSERT OrderStatusHistory

  Step 7  Convert total to paise
            long amountPaise = (long)Math.Round(totalAmount * 100m, AwayFromZero)
            Safe decimal arithmetic — no floating-point drift.

  Step 8  Call Razorpay Orders API
            POST https://api.razorpay.com/v1/orders
            Body: { amount: <paise>, currency: "INR", receipt: "GM-{id}-{date}" }
            Auth: Basic Auth (KeyId:KeySecret, Base64-encoded)
            On failure → VoidOrderAsync (restore inventory, cancel order)
                        → throw PaymentGatewayException → 503

  Step 9  Persist payment attempt
            PaymentRepository.CreateAsync
            Status = "Initiated", GatewayOrderId = razorpay order_XXXX

  Step 10 Return response to browser (via MVC proxy)
            { internalOrderId, internalOrderNumber, razorpayOrderId,
              amountPaise, currency, keyId (PUBLIC only),
              customerName, customerEmail, customerPhone }
            *** KeySecret is never included in any response. ***

6. PAYMENT VERIFICATION LOGIC  (RazorpayService.VerifyPaymentAsync)
────────────────────────────────────────────────────────────────────────────────

  Step 1  Validate input — razorpay_order_id, payment_id, signature required.

  Step 2  HMAC-SHA256 signature verification
            expected = HMAC_SHA256(KeySecret, orderId + "|" + paymentId)
            Compared with constant-time CryptographicEquals to prevent
            timing attacks.

  Step 3  Load payment record by GatewayOrderId.

  Step 4  Idempotency — if already Captured, return success immediately.

  Step 5  Load internal order (ownership check — userId must match).

  Step 6  Verify with Razorpay Payments API
            GET https://api.razorpay.com/v1/payments/{paymentId}
            Validate:
              - rzPayment.OrderId matches razorpayOrderId
              - rzPayment.Amount matches expected paise (server-side)
              - rzPayment.Currency == "INR"
              - rzPayment.Captured == true OR rzPayment.Status == "captured"

  Step 7  Mark Captured
            PaymentRepository.CaptureAsync (atomic transaction):
              UPDATE Payments SET Status='Captured'
              UPDATE Orders   SET PaymentStatus='Paid'

  Returns: { success, message, internalOrderId, orderNumber,
             orderStatus, paymentStatus }

7. WEBHOOK PROCESSING  (POST /api/v1/payments/razorpay/webhook)
────────────────────────────────────────────────────────────────────────────────

  1. Read raw request body BEFORE any framework body reader.
  2. Validate X-Razorpay-Signature header using WebhookSecret (HMAC-SHA256).
  3. Parse event type and event ID from JSON.
  4. RecordWebhookEventAsync — idempotency: duplicate GatewayEventId → skip.
  5. Handle event:
       payment.captured → CaptureAsync (idempotent)
       payment.failed   → MarkFailedAsync
       others           → logged at Debug, acknowledged with 200
  6. MarkWebhookEventProcessedAsync
  7. On processing error → return 500 (Razorpay will retry)

  Webhook URL:
    https://bloomier-aspersively-patrica.ngrok-free.dev/api/v1/payments/razorpay/webhook

  Register in Razorpay Dashboard:
    Settings → Webhooks → Add New Webhook
    Events: payment.captured, payment.failed
    Secret: (value from Razorpay:WebhookSecret in appsettings.json)

9. SQL SCHEMA  (database/012_RazorpayPayments.sql)
────────────────────────────────────────────────────────────────────────────────

  Table: Payments
    Id               INT IDENTITY PK
    OrderId          INT NOT NULL  FK → Orders(Id)
    GatewayName      NVARCHAR(50)  e.g. "Razorpay"
    GatewayOrderId   NVARCHAR(200) Razorpay order_XXXX
    GatewayPaymentId NVARCHAR(200) Razorpay pay_XXXX (set on capture)
    Amount           DECIMAL(10,2)
    Currency         NVARCHAR(5)   "INR"
    Status           NVARCHAR(30)  Initiated | Captured | Failed
    Method           NVARCHAR(50)  upi | card | netbanking | wallet
    FailureReason    NVARCHAR(500)
    CreatedAt        DATETIME2
    UpdatedAt        DATETIME2
    UNIQUE INDEX on GatewayOrderId

  Table: PaymentWebhookEvents
    Id               INT IDENTITY PK
    PaymentId        INT NULL FK → Payments(Id)
    GatewayName      NVARCHAR(50)
    EventType        NVARCHAR(100) payment.captured | payment.failed
    GatewayEventId   NVARCHAR(200) Razorpay event ID (idempotency key)
    RawPayload       NVARCHAR(MAX)
    ProcessedAt      DATETIME2 NULL
    ProcessingError  NVARCHAR(1000) NULL
    ReceivedAt       DATETIME2
    UNIQUE INDEX on GatewayEventId

11. SECURITY CONTROLS
────────────────────────────────────────────────────────────────────────────────

  1. KeySecret never leaves the API server process.
  2. JWT never leaves the Web server process (HttpOnly cookie only).
  3. Session key (cart) never leaves the Web server process.
  4. All MVC proxy endpoints require [ValidateAntiForgeryToken].
  5. Payment amounts are calculated server-side — browser values ignored.
  6. Webhook signature validated with HMAC-SHA256 before any processing.
  7. Duplicate webhook events rejected via GatewayEventId unique constraint.
  8. Payment ownership verified: userId must own the order.
  9. Razorpay payment status must be "captured" before marking Paid.
  10. Constant-time signature comparison (CryptographicEquals) prevents
      timing attacks.
  11. Smoke-test endpoint disabled in non-Development environments.

12. BUGS FIXED DURING INTEGRATION
────────────────────────────────────────────────────────────────────────────────

  Bug 1: HTTP 503 caused by ngrok interstitial (highest priority)
    Root cause: ApiSettings:BaseUrl in appsettings.Development.json was set to
                the ngrok tunnel URL. Web→API calls went through ngrok, which
                returned an HTML interstitial page (not JSON). JsonSerializer
                threw JsonException, caught as generic Exception → HttpRequestException
                → CheckoutController returned 503.
    Fix:       Restored BaseUrl to http://localhost:5000.
               Added ngrok-skip-browser-warning header to all HttpClients
               as a safety net for future tunnel testing.

  Bug 2: Gateway errors (PaymentGatewayException) mapped to HTTP 422 not 503
    Root cause: RazorpayService threw InvalidOperationException for ALL errors
                including network failures. PaymentsController mapped
                InvalidOperationException → 422 Unprocessable Entity.
    Fix:       Introduced PaymentGatewayException. Only thrown for gateway
               failures. PaymentsController catches it → 503.
               InvalidOperationException reserved for business rule violations → 422.

  Bug 3: Dangling Pending orders on every Razorpay failure
    Root cause: CreateOrderAsync inserted the internal Order (step 6) before
                calling Razorpay (step 8). On gateway failure the order was
                left Pending with deducted inventory and no payment row.
                Every retry created a new orphaned order.
    Fix:       Wrapped CallRazorpayCreateOrderAsync in try/catch.
               On failure, VoidOrderAsync restores inventory and cancels
               the order before re-throwing.

  Bug 4: Duplicate-click could bypass isSubmitting guard
    Root cause: updatePaymentUI() reassigned primaryBtn.onclick on every call,
                including error recovery paths while a request was in flight.
                A rapid radio-button change then click could slip through.
    Fix:       updatePaymentUI() early-returns when primaryBtn.disabled===true.

  Bug 5: ErrorResponse never populated TraceId
    Root cause: All ErrorResponse(message) calls omitted the TraceId parameter.
    Fix:       All catch blocks now pass HttpContext.TraceIdentifier as TraceId.
               Development 503 responses also include GatewayStatusCode and
               GatewayErrorCode for diagnosing Razorpay failures without
               needing console access.

  Bug 6: No actionable detail in Razorpay error logs
    Root cause: Gateway errors logged only the raw body as one blob.
    Fix:       ExtractRazorpayError() pulls error.code and error.description
               from Razorpay's JSON envelope and logs them as separate fields.
               Network errors log the inner exception type.
